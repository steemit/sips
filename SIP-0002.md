# Steem Hardfork Proposal: Agent Keys
### Capped, delegable on-chain identities for AI agents

> **Status:** Draft v0.1 — open for community review
> **Date:** 2026-11-04
> **Scope:** Consensus-layer change to the Steem blockchain (steemit/steem core)
> A full technical specification and decision log will be published together with the code.

---

## 1. Abstract

Agent Keys introduce a new kind of on-chain identity — the **agent slot** — that is entirely separate from the existing `owner`, `active` and `posting` authorities. An account owner can mint up to 16 agent identities, bind a key to each, and give that key to an AI agent (or any automated service) with **hard, protocol-enforced spending caps** and a **fixed, deliberately narrow** set of capabilities.

Unlike today's practice of handing an `active` key to a bot — which grants the bot the power to change account authorities, power down, place market orders, create escrows and drain the account — an agent key is structurally incapable of any of that. Its only spending channel is a dedicated `agent_transfer` operation bounded by per-transaction and weekly limits, denominated separately in STEEM and SBD.

The proposal also introduces a small, opt-in economic layer: short and pattern-based "vanity" agent IDs can be purchased on-chain for SBD, with fees going to the SPS treasury (`steem.dao`).

This is a hardfork-gated change. Every number below is a proposal parameter and can still be adjusted based on community feedback.

---

## 2. Motivation

Three trends make this timely:

1. **AI agents are becoming first-class users.** An agent that posts, curates, comments and pays for services needs to *sign transactions*. Today the only practical options are giving it an `active` key (unbounded power) or a `posting` key (no spending power at all). There is no middle ground.
2. **The blast radius of a compromised key is unbounded.** An `active` key can change the account's own `active` authority (`account_update` requires only `active` when the `owner` field is absent), add a fresh unlimited key, and empty the wallet. Escrow transfers and self-traded limit orders are additional exfiltration paths that a budget-checked key would still leave open.
3. **Users want to bound, not eliminate, agent spending.** Capabilities such as weekly budgets, per-transaction caps and frozen assets are what people actually configure when they deploy agents — and today they must be enforced off-chain, where they can be bypassed by broadcasting directly to any node.

Agent Keys move that enforcement **into consensus**, where it cannot be bypassed.

---

## 3. Why not extend existing authorities?

Two alternatives were evaluated and rejected:

- **Budget checks on `active` keys (a "limited active key").** Rejected because `active` retains structural powers that no budget can contain: `account_update` lets the key add a brand-new unlimited active key; `withdraw_vesting`, `escrow_transfer`, and wash-trading via limit orders are additional outflow paths. Any check-based whitelist has to remember to block every one of them — including future operations — and a single omission restores full power.
- **A fourth authority tier in the owner > active > posting hierarchy.** Rejected because it requires redefining satisfaction relations across all tiers and touching every place the authority model is enumerated (signature checks, APIs, wallets, tests). The dedicated-operation approach below achieves the same structural isolation with a much smaller consensus surface.

**Chosen design:** an independent identity whose signing power exists *only* through a dedicated family of operations. No existing operation ever asks an agent key for anything.

---

## 4. The Agent Slot

- An account may hold **up to 16 agent slots concurrently** (transfers free a slot; unbinding does not).
- Each slot has a globally unique, never-reused numeric identity: **`agent_id`** (uint32).
- Ordinary registration assigns the next available id from a consensus-state allocator starting at **10001**. IDs **1–10000 are system-reserved** and never issued or sold.
- Slots are **never deleted**. Unbinding clears the key, limits and counters but keeps the identity.
- Each slot has an optional **alias** (unique within the account, display-only, renamable).
- Rebinding a new key to an existing slot is a **rekey**: the identity and the in-progress weekly counters are preserved.
- Slots are **transferable** between accounts (see §9): the id moves; the key, limits, counters and alias are wiped; the recipient must explicitly rebind. Content-management rights do **not** follow the id (§6).

---

## 5. Capabilities — what an agent key can and cannot do

**Can:**

| Operation | Purpose | Notes |
|---|---|---|
| `agent_transfer` | Pay others in STEEM/SBD | The **only** spending channel; subject to all caps (§7) |
| `agent_vote` | Upvote/downvote | Full weight range |
| `agent_comment` | Create and edit posts/comments | Edits keep original attribution |
| `agent_delete_comment` | Delete content | Only content **created by this very agent identity**, and only while the slot still belongs to the author account (§6) |
| `agent_comment_options` | Payout settings, beneficiaries | Same scope rule; existing "tighten-only" rules apply |
| `agent_claim_reward_balance` | Claim pending rewards into the account | Never consumes budget (inflow, not outflow) |

**Cannot — structurally, not by policy:**

- Change any authority (`account_update` / `account_update2`), power down (`withdraw_vesting`), create or cancel market orders, create escrows, delegate vesting shares, set withdrawal routes, vote witnesses, or broadcast `custom_json` with active authorization.
- Satisfy `owner`, `active` or `posting` requirements anywhere in the protocol. Agent keys exist in **none** of the three tiers; the posting-fallback chain is untouched.
- One key cannot be an agent key and a member of any authority of the same account at the same time (bidirectional overlap guard).

---

## 6. Content scope rule

Agent content management is scoped with two simultaneous conditions:

```
comment.agent_id == operation.agent_id        # created by this agent identity
comment.author   == slot.account              # slot still belongs to the author
```

Consequences: human-authored content is untouchable by agents; after a slot transfer, neither the old owner (no longer owns the id) nor the new owner (account mismatch) can manage the old content — only the account's own posting/active keys can. Content provenance is stored on-chain (`agent_id` plus the creating public key) so auditability survives key rotation.

---

## 7. Budgets

- Limits are configured per slot as **four mandatory fields**: `steem_single`, `steem_weekly`, `sbd_single`, `sbd_weekly`. There is deliberately **no "unset" state** — every field must be explicitly filled; an explicit `0` freezes that asset.
- STEEM and SBD are budgeted independently; a single `agent_transfer` can only move one asset.
- The weekly window is the **UTC calendar week** (Monday 00:00), computed from block time (the only consensus-safe clock); resets are lazy — two counters and one timestamp per slot.
- Checks and deductions are **atomic at the transaction level**: caps are verified before operations are applied and counters are incremented after the whole transaction succeeds; any failure rolls back everything. Overspending transactions are rejected at mempool admission.
- Rekeying preserves counters; unbinding and transferring reset them (explicit owner actions).

## 8. Operations overview

| # | Operation | Authority | Purpose |
|---|---|---|---|
| 1 | `set_agent_key` | owner | Create a slot (or rekey / change limits / rename alias) |
| 2 | `unbind_agent_key` | owner | Remove the bound key, wipe limits and counters, keep the id |
| 3 | `buy_agent_id` | owner | Purchase a vanity `agent_id` for SBD (§9) |
| 4 | `transfer_agent_id` | owner | Transfer a slot to another account (auto-unbind) |
| 5 | `agent_transfer` | agent | Capped STEEM/SBD transfer |
| 6 | `agent_vote` | agent | Vote |
| 7 | `agent_comment` | agent | Post / edit |
| 8 | `agent_delete_comment` | agent | Delete own content |
| 9 | `agent_comment_options` | agent | Payout settings on own content |
| 10 | `agent_claim_reward_balance` | agent | Claim rewards |

All ten are new wire variants gated by the hardfork. Signature verification is performed at **(account, agent_id) granularity**: each operation declares the exact slot it acts for, and only that slot's current key may sign for it. Distinct error codes distinguish "slot not found", "slot owned by another account", "slot unbound" and "missing signature", so clients and indexers can diagnose failures precisely. Signatures not used by any declared operation are rejected as irrelevant, exactly like the existing `tx_irrelevant_sig` rule.

## 9. Vanity agent IDs (economic layer)

**Classification.** Only the *suffix* of the decimal id is inspected (matching the familiar "888 tail" convention), with one whole-number exception: 6-digit palindromes. Three levels:

- **L1** — trailing triple (`xxx888`), trailing 3-run sequence (`123`/`987`), or trailing `AABB`/`ABAB`/`ABBA` pattern
- **L2** — trailing quadruple, trailing 4–5-run sequence, or a 6-digit palindrome
- **L3** — trailing quintuple or longer, or a 6-run sequence

Measured rates: since the rules only depend on the last six digits, **7+ digit IDs are exactly 5.300% vanity**; the 6-digit range is 5.388% because of the 900 palindromes (795 net additions); allocator skip cost is ≈0.057 skips per registration. Full enumeration data ships with the code.

**Allocation.** The allocator skips all vanity numbers, so free registrations never receive them. Vanity ids can be bought at any time — including numbers the allocator already skipped — for **SBD**, at fixed prices per level:

| Level | Mainnet | Testnet |
|---|---|---|
| L1 | 10 SBD | 1 SBD |
| L2 | 100 SBD | 3 SBD |
| L3 | 1000 SBD | 5 SBD |

All fees go to the **SPS treasury (`steem.dao`)**. Purchase is permanent (slots are never deleted) and counts against the 16-slot limit. Reserved ids 1–10000 are never sold or issued.

**Transfers.** Slots can be transferred to another account by the owner in a single on-chain operation; pricing and delivery between users happen off-chain and are outside the scope of this proposal. The recipient receives an empty slot (no key, no limits, no alias) and must rebind it.

## 10. Compatibility and activation

- New operations are new wire variants; all nodes must upgrade. The feature is gated behind the next hardfork and inactive until then.
- Activation on mainnet requires the usual **17/21 witness version-signal** approval.
- The full sequence will be exercised on the testnet first: object and allocator, registration/unbinding, `agent_transfer` with budgets, then the content operations, APIs and virtual-operation event stream.

## 12. Open questions for the community

1. **Price points** for vanity ids (10/100/1000 SBD) — too high, too low?
2. **The 16-slot concurrent cap** — sufficient for multi-agent users?
3. **Capability scope** — should later hardforks add agent variants of `transfer_to_savings` or app-specific operations? Which ones?
4. **Budget window** — is a UTC calendar week the right granularity, or should rolling windows be considered?
5. **Reserved range** — should ids 1–10000 ever be released, and under what governance?
6. **API surface** — what do wallets, explorers and agent frameworks need beyond the proposed `get_agent_keys` / `get_agent` queries?

Feedback is welcome on any of the above, and on the specification as a whole. The detailed technical specification (object fields, validation rules, invariants, test matrix) will be published alongside the implementation on the testnet.
